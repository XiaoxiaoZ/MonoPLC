# MonoPLC: A Side-Effect-Free Event-Driven PLC Architecture

MonoPLC is an experimental, modern software architecture applied to the world of industrial control (Programmable Logic Controllers, PLCs). Built natively in TwinCAT 3 (IEC 61131-3 Structured Text), it radically transforms traditional PLC design patterns by migrating them into formal mathematical structures.

## Motivation
Traditional PLC code is often heavily procedural and state-mutating. Code checks `IF Temp > 80 THEN TurnOnValve()`, creating direct entanglement between logical condition, physical I/O mapping, and task scheduling. As projects scale, especially when asynchronous network protocols (like MQTT or REST integrations) are introduced, these procedural side-effects lead to "Zombie States", race conditions, and watchdog timeouts due to blocking network calls acting natively on the millisecond PLC thread.

## The Solution: Side-Effect Separation via Monoids
MonoPLC proposes a simple but powerful core philosophy: **completely decouple deterministic logic from the execution of side effects**.

Instead of writing an execution block that mutates a pin, the core logic is a Deterministic Logic Block (`FB_SimpleLogic`). It receives an `Input_Event` and returns its decisions as a declarative data structure called a `DUT_Effect`. 

By treating all external impacts—whether it's an HMI command or a network request—as Monoids, we can mathematically combine and fold them. Because the core logic never directly touches hardware IO or blocking network libraries, developers gain profound **architectural freedom**.

For instance, this freedom allows us to easily implement a **Single-Threaded Asynchronous Event Loop**—functionally identical to a Node.js engine or modern Actor model framework—running natively on a Beckhoff RT kernel:
1. **Unification of Inputs and Outputs**: Physical digital inputs, HMI touch commands, background IoT network requests, and even internal logic effects are uniformly wrapped as `DUT_Effect` Events.
2. **Event Recursion**: Effects generated by the deterministic logic are not immediately executed. They are pushed back to the bottom of the `Event_Bus` queue to be dispatched in turn.
3. **Deterministic Logic Core**: Logic modules never directly read hardware sensors or delay timers. They only compute state transitions and consequences based on the popped events.

### Problem

Industry 4.0 pushes IoT devices, AI services and operator panels into control loops that were never designed to accept them. The NAMUR Open Architecture (NOA) draws the line between Core Process Control (CPC), which must stay deterministic, and Monitoring & Optimization (M+O), which is everything non-real-time. NOA says M+O requests must be verified before they enter CPC, but it does not say how several M+O inputs should be *combined* once inside the runtime, or what should hold when one of them goes silent. Existing PLC work does not fill that gap either: object-oriented patterns and IEC 61499 structure components rather than constrain their composition, the Asset Administration Shell standardises the information model but not the algebra, and the algebraic PLC work that does exist (Šusta) is offline static analysis.

### Approach

MonoPLC enforces the three Monoid axioms — closure, associativity, identity — as *architectural constraints* rather than as a proof technique. Three layers:

| Layer | Role |
| --- | --- |
| 1. PLC (TwinCAT / ST) | Real-time control logic; all I/O is an Effect Monoid element |
| 2. Bridge server (Python / FastAPI) | Monoid fold into state, homomorphism φ, whitelist (VoR) on the way in |
| 3. M+O sources | HMI buttons, LLM agent (Ollama), MQTT device — all emit the same Effect type |

Four design decisions carry the weight:

- **One Effect type for everything.** `DUT_Effect` (11 effect types) with array concatenation and the empty array as identity. Closure forces every source to speak the same language, which is what makes new sources free.
- **A Product Monoid per domain.** Temperature uses bounded concatenation, humidity uses (ℝ, +, 0), pressure uses (ℝ, max, 0). Domains compose component-wise, so they cannot interfere.
- **Absent source ↦ identity.** A disconnected source contributes ε, and ε ⊕ a = a at *every* composition point. No per-source null checks, and no single missed check to cause undefined behaviour.
- **A homomorphism across the boundary.** φ maps PLC effect lists to middleware state dictionaries, with φ(A ++ B) = φ(A) ⊕ φ(B) and φ([]) = {}. It is self-verifying: two computation paths on the same input, no hand-written expected outputs.

### Results

Associativity is proved to survive the bounded array: `trunc(N, A ++ B)` is still associative, so the fixed 20-element ST array does not break the algebra. The Product Monoid inherits its axioms, so new domains need no new proof.

Extensibility was measured on a running system, not argued:

| Change | Cost |
| --- | --- |
| New M+O source (MQTT) | ~30 lines in a new file; 0 lines changed in Layers 1 and 2 |
| New monitoring dimension (`peak_temp`) | 1 line of component registration |
| New control domain (pressure) | ~148 new + 12 wiring lines; `FB_SimpleLogic` and `FB_HumidityLogic` untouched; all 53 prior tests pass |

Timing was measured with TwinCAT TE1300 Scope View over 13,705 cycles at a 10 ms configured cycle:

| Metric | Value |
| --- | --- |
| Mean execution time | 44.7 μs |
| p99 | 87.1 μs |
| Max | 1118.3 μs |
| Worst-case cycle utilisation | 11.18% |
| Event bus overflow count | 0 |

Under stress (200 injected effects, 50 alternating start/stop commands at 50/s, 100 random setpoint changes in 5 s) the input queue depth stayed at 0 and control was unaffected. Disconnecting the LLM mid-run changed nothing — the identity element absorbed it. The suite is 64 tests over 8 files, roughly 1300 Hypothesis-generated examples, zero failures.

### Scope and limits

The paper claims feasibility and extensibility within IEC 61131-3, not industrial-scale readiness. One scenario, one vendor (Beckhoff), no formal WCET analysis, and no authentication, rate limiting, or IEC 62443 threat modelling. Buffer overflow is data loss rather than absence of input, so the fail-passive guarantee does not cover it — Section 5.7 sketches deduplicating, priority-aware, and budget-limited Monoids as alternatives. The algebraic guarantees cover input *composition*; the control logic inside a function block is ordinary sequential code validated by testing.
