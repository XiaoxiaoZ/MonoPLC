# MonoPLC: A Pure Functional Event-Driven PLC Architecture

MonoPLC is an experimental, modern software architecture applied to the world of industrial control (Programmable Logic Controllers, PLCs). Built natively in TwinCAT 3 (IEC 61131-3 Structured Text), it radically transforms traditional PLC design patterns by migrating them into formal mathematical structures.

## Motivation
Traditional PLC code is often heavily procedural and state-mutating. Code checks `IF Temp > 80 THEN TurnOnValve()`, creating direct entanglement between logical condition, physical I/O mapping, and task scheduling. As projects scale, especially when asynchronous network protocols (like MQTT or REST integrations) are introduced, these procedural side-effects lead to "Zombie State Machines", race conditions, and watchdog timeouts due to blocking network calls acting natively on the millisecond PLC thread.

## The Solution: Side-Effect Separation via Monoids
MonoPLC proposes a simple but powerful core philosophy: **completely decouple pure calculation logic from the execution of physical side effects**.

Instead of writing an execution block that mutates a pin, the core logic is a strict pure function (`FB_SimpleLogic`). It receives an `Input_Event` and returns its decisions as a declarative data structure called a `DUT_Effect`. 

By treating all external impacts—whether it's an HMI command or a network request—as Monoids, we can mathematically combine and fold them. Because the core logic never directly touches hardware IO or blocking network libraries, developers gain profound **architectural freedom**.

For instance, this freedom allows us to easily implement a **Single-Threaded Asynchronous Event Loop**—functionally identical to a Node.js engine or modern Actor model framework—running natively on a Beckhoff RT kernel:
1. **Unification of Inputs and Outputs**: Physical digital inputs, HMI touch commands, background IoT network requests, and even internal logic effects are uniformly wrapped as `DUT_Effect` Events.
2. **Event Recursion**: Effects generated by the pure logic are not immediately executed. They are pushed back to the bottom of the `Event_Bus` queue to be dispatched in turn.
3. **Pure Function Core**: Logic modules never directly read hardware sensors or delay timers. They only compute consequences based on the popped events.
